# JumpPi

NixOS configuration for `jumppi`, a small ARM (aarch64) machine that acts as a
**jump server / bastion host**, reachable exclusively through a
[NetBird](https://netbird.io) mesh network.

The idea: no public ingress other than what the mesh gives you. Devices on your
NetBird network can SSH into `jumppi`, and from there reach hosts on the
internal network that are not exposed otherwise.

## Layout

| File                        | Purpose                                                                |
| --------------------------- | ---------------------------------------------------------------------- |
| `flake.nix`                 | Flake inputs and the host definition (`nixosModules.default`)          |
| `hardware-configuration.nix`| Disks, kernel modules, platform — generated by `nixos-generate-config` |
| `services-configuration.nix`| SSH, NetBird, `systemd-resolved`                                       |
| `user-configuration.nix`    | The `pi` user, authorized SSH keys, packages, sudo policy              |

## What is configured

**Platform**

- `aarch64-linux`, booted via `boot.loader.generic-extlinux-compatible`
  (typical for Raspberry Pi / U-Boot based boards).
- Hostname `jumppi`, timezone `Europe/Berlin`, locale `en_US.UTF-8`,
  German console keymap.

**SSH (hardened)**

- Key-only authentication: `PasswordAuthentication = false`,
  `KbdInteractiveAuthentication = false`.
- `PermitRootLogin = no` — log in as `pi` and escalate with `sudo`.
- Prefix-free passwordless sudo for the `wheel` group
  (`security.sudo.wheelNeedsPassword = false`).
- Note that `openFirewall = true` opens port 22 on **all** interfaces, not just
  `wt0`. If the machine sits on an untrusted LAN, restrict this to the NetBird
  interface.

**NetBird**

- One client interface, `wt0`, listening on UDP `51821`, with both the host
  firewall and NetBird's internal firewall opened.
- `services.resolved` is enabled because the NetBird client relies on it for
  DNS resolution of peers.
- `pi` is a member of the `netbird-wt0` group, so it can inspect and control the
  client without root.

**Tooling**

- Management: `git`, `vim`, `neovim`, `nano`, `htop`, `tree`.
- Network/DNS debugging: `nmap`, `netcat`, `iperf`, `tcpdump`, `mtr`,
  `dnsutils`, `curl`, `wget`, `httpie`, `netbird`.

## Before you deploy

The files are a template and contain placeholders that **must** be changed:

1. **SSH key** — `user-configuration.nix` ships a sample
   `ssh-ed25519 AAAA...` key. Replace it with your own public key, otherwise
   nobody (including you) can log in.
2. **Disk UUID** — `hardware-configuration.nix` uses the placeholder
   `/dev/disk/by-uuid/44444444-4444-4444-8888-888888888888`. Regenerate the file
   on the target hardware with `nixos-generate-config`, or the system will not
   boot.
3. **NetBird enrollment** — the client is configured but not enrolled. Claims
   are not stored in this repo (and should not be): run

   ```sh
   sudo netbird up --setup-key <key>
   ```

   or use the SSO flow. The resulting state lives in `/var/lib/netbird`.
4. `system.stateVersion = "26.11"` — leave it alone unless you are deliberately
   migrating; it gates stateful migrations, it is not a nixpkgs pin.

## Building and deploying

The flake exports the host as a **module** (`nixosModules.default`), not as a
`nixosConfigurations.<name>`. You can either import it from another flake, or
add an output to build it directly:

```nix
outputs = inputs: {
  nixosConfigurations.jumppi = inputs.nixpkgs.lib.nixosSystem {
    system = "aarch64-linux";
    modules = [ inputs.self.nixosModules.default ];
  };
};
```

Then deploy over the network (from an `aarch64-linux` host, or with
`boot.binfmt.emulatedSystems = [ "aarch64-linux" ]` for cross-building):

```sh
nixos-rebuild switch --flake .#jumppi --target-host pi@jumppi --use-remote-sudo
```

For a first install on blank storage, `nixos-anywhere` is the usual route:

```sh
nixos-anywhere --flake .#jumppi root@<temporary-ip>
```

Note that the new machine is only reachable on the NetBird address once
`netbird up` has succeeded, so keep out-of-band access (serial console, local
keyboard) available until then.

## Using the jump host

```sh
# On a peer in the NetBird network
ssh -J pi@jumppi internal-host

# Or as a SOCKS proxy for arbitrary traffic
ssh -D 1080 -N pi@jumppi
```

`ssh -J` requires the target's key to be present on `jumppi`, so either copy your
key there or use agent forwarding (`ForwardAgent yes`) — forwarding to a shared
bastion is a deliberate trade-off worth deciding on explicitly.
